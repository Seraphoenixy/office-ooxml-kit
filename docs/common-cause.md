# 共因分析：两个项目为什么都在重复造 Office 轮子

`D:\project\DO-178C-review-workflow` 与 `D:\project\form_generate` 各自实现了一套 DOCX 结构提取，
外加一套写回逻辑。2026-11 的合并复查把两边的实现和跑过的语料放在一起比对，结论是：
**两边都在解决同一个问题，而且两边都只解决了一半。**

## 一、共因：问题本身被低估了

重复造轮子通常被归因为「没人先做一个库」。真实原因是**这件事看起来比实际简单**：

| 看起来 | 实际 |
| --- | --- |
| 打开 zip，读 `word/document.xml`，取 `w:t` | 文字可能在 `w:t`、`m:t`（公式）、`w:instrText`、`w:txbxContent` 里，还要处理 `w:tab`/`w:br` |
| 段落文字就是内容 | 内容可能是段落、表格行、内容控件（`w:sdt`）里的单元格，三者交错在同一序列里 |
| 「第 1 张表第 2 行」能定位 | 行号是表内序号；表格还可能在单元格里嵌套，光靠序号无法唯一标识 |
| 标题按样式名判断 | 标题由 `outlineLvl` 决定，且要沿 `basedOn` 继承链查；目录样式（`toc`/`目录`）不是标题 |
| 自动编号读 `numPr` 就行 | `numId` 与 `ilvl` 可能分别来自不同祖先；`startOverride` 只在首次出现时生效；空段落是否推进计数器要按 Word 行为定 |
| 写回就是改 XML | 改完必须保住 38 个命名空间前缀，否则 Word 报「文件已经损坏」 |

每一格都是一次踩坑。坑是同一个坑，只是撞的人不同、撞的时间不同。

## 二、共因的四种具体表现

### 1. 只取 `w:t`，公式被当成空白

`docx.ps1` 的 `Text()` 只匹配 `.//w:t | .//w:tab | .//w:br`。OMML 公式的文字在 `m:t`，
局部名同样是 `t`，但命名空间是 `officeDocument/2006/math`。

语料比对里 7 处单元格差异全部由此产生：

```
w:t = '无符号，分辨率为，表示范围为0- '
m:t = '5×10-6 m/m' 、'1.275×10-3m/m'
PowerShell 得到：无符号，分辨率为，表示范围为0-
Python   得到：无符号，分辨率为5×10-6 m/m，表示范围为0- 1.275×10-3m/m
```

后果不是「少了几个字」，而是**技术指标被静默抹掉**：分辨率、量程、`σpr_gnd`、`B1`~`B4`
这些字段在比对结果里变成空串或 `--`。审阅人看到的是一份「两边都为空所以没有差异」的表格。

### 2. 编号差一位，因为空段落也推进计数器

`BDS2230DG009 北斗导航软件测试规程A2.docx` 里，Python 与 PowerShell 对同一段给出：

```
Python   5.4.1 内存使用大小测试
PowerShell 5.4.2 内存使用大小测试
```

用 Word 自己的 `ListFormat.ListString` 裁定——**Word 显示 `5.4.1`**，Python 对。
PowerShell 在「有编号样式但正文为空」的段落上仍递增了计数器，于是一路偏移。

这类差异最危险的地方是它**看起来像正常的版本差异**：`5.4.1 → 5.4.2` 完全可能是"这一版插入了一节"。
审阅人会把它当成实质变更去写备注，而实际上文档一个字都没动。

### 3. 同名不同源：两个项目共用词表，却各写各的判断

`review.py` 与 `docx.ps1` 都在回答「哪些内容文本比较验证不了」。两边词表几乎一样
（修订、文本框、公式、嵌套表格、内容控件、图片、页眉页脚），但实现方式不同：

- `docx.ps1` 用 XPath 计数；
- `review.py` 用 `next(tree.iter(w+'drawing'), None)` 只判断"有没有"。

结果：前者报「32 处图片、7 处 OLE 预览」，后者只报「含图片或图形」。
后者更接近"提个醒"，但**同一条风险，两个项目给出不同精度**，评审记录无法互相比对。

### 4. 写回：命名空间前缀必须逐个保住

`xml.etree.ElementTree` 往返会丢掉约 34 个命名空间前缀，`mc:Ignorable` 里的
`w14 w15 ...` 是按名字引用前缀的，前缀没了 Word 直接判定文件损坏。这不是"写法不好"，
而是 stdlib ET 的设计取舍。任何自己写回的项目都会撞上这一条——撞上之后的第一反应通常是
"换个写法试试"，而不是"换库"。

## 三、为什么两边的坑没有互相传递

两个项目之间没有共享代码，连共享的**结论**都没有：

- `form_generate` 的 `docx.ps1` 注释里写着「只取 w:t 会得到空串」，但它修的是**单元格序号**那一种情形，
  没意识到公式也是同一种情形；
- `DO-178C` 的 `review.py` 注释里写着「那是工具缺口，不是评审人该做的事」，它补的是**样式**，
  没补公式；
- 两处都写了「自动编号未展开」的警告，但两处都没有把编号算准。

同一个知识点，在两份代码里各写了一遍，各漏了一半。**这就是共因的直接成本。**

## 四、结论

重复造轮子的根因不是"缺少抽象"，而是**这份知识的边界没人划清**：
哪些是 Word 的既有行为（必须照做）、哪些是项目的私有约定（可以各写各的）、
哪些是踩过的坑（必须共享）。

所以通用组件的重点不是"把代码抽出来"，而是：

1. **把 Word 语义钉成契约**（`docx-model-v1`），谁读都得到同一份结构；
2. **把踩过的坑钉成测试**，每条断言对应一个具体缺陷，回归时不会悄悄退化；
3. **把判据只留一份实现**，项目可以有自己的块形状，但「什么验证不了」的答案必须一致。

第 3 条正是本次改动的收口处：`DO-178C` 保留自己的 `{id, text, location, style}` 块形状
（它的消费方是评审记录，不是 CR 生成），但版面风险清单改由 `office_ooxml_kit.scan()` 提供。
块形状可以不同，判定标准不能不同。
